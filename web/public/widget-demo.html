cainban embeddable widget

One <script> tag plus a <div data-cainban-widget> renders a live board-status card on any site. Each widget mounts into its own Shadow DOM, so the host page's Comic Sans and letter-spacing above never touch it.

Minimal usage

<script src="cainban-widget.js"></script>
<div data-cainban-widget data-repo="owner/repo"></div>

Live examples

All attributes

data-repo        owner/repo (required)
data-api         MCP endpoint URL (optional; defaults to <board-url>/mcp)
data-token       read-only bearer token (optional; for authed servers)
data-board-url   full board URL opened on click (optional)
data-theme       "light" | "dark" (optional; omit to follow the OS)
data-poll        refresh interval in seconds (optional; 0 disables; default 30)
data-bar         "true" | "false" mini-board bar (optional; default true)

Private boards: read-only tokens

A public MCP server rejects an unauthenticated read. To surface a private board, mint a read-only widget token and pass it as data-token. A widget token:

  • is scoped to exactly one repo;
  • can call only the read tools (list_tasks, get_task, list_activity) — never a write;
  • has a wt_ prefix and an expiry (default 30 days, max 365);
  • can be revoked by id, so a leaked token can be cut off.

Create one from an authenticated MCP client (you must already be authorized for the repo) via the create_widget_token tool, list them with list_widget_tokens, and revoke with revoke_widget_token. Then embed it: 

<div data-cainban-widget
     data-repo="owner/repo"
     data-api="https://mcp.example.com"
     data-token="wt_abc123..."></div>

The token is sent as Authorization: Bearer wt_…. Because it is read-only and single-repo, a write attempt is rejected server-side with 403 Forbidden before it runs.

Inject widgets after load? Call window.cainbanWidget.mount() to upgrade any new [data-cainban-widget] elements.
